# cli-validate
Define `outline-spec validate` behavior for validating changes and specs with actionable remediation guidance and structured output.

1. Validation SHALL provide actionable remediation steps: Validation output SHALL include specific guidance to fix each error, including expected structure, example headers, and suggested commands to verify fixes.
  a. No deltas found in change: WHEN validating a change with zero parsed deltas THEN show error "No deltas found" with guidance: Explain that change specs must include `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`, or `## RENAMED Requirements` Remind authors that files must live under `outline-spec/changes/{id}/specs/<capability-path>/spec.md` Include an explicit note: "Spec delta files cannot start with titles before the operation headers" Suggest running `outline-spec change show {id} --json --deltas-only` for debugging
  b. Missing required sections: WHEN a required section is missing THEN include expected header names and a minimal skeleton: For Spec: `## Purpose`, `## Requirements` For Change: `## Why`, `## What Changes` Provide an example snippet of the missing section with placeholder prose ready to copy Mention the quick-reference section in `outline-spec/AGENTS.md` as the authoritative template
  c. Missing requirement descriptive text: WHEN a requirement header lacks descriptive text before scenarios THEN emit an error explaining that `### Requirement:` lines must be followed by narrative text before any `#### Scenario:` headers Show compliant example: "### Requirement: Foo" followed by "The system SHALL ..." Suggest adding 1-2 sentences describing the normative behavior prior to listing scenarios Reference the pre-validation checklist in `outline-spec/AGENTS.md`
2. Validator SHALL detect likely misformatted scenarios and warn with a fix: The validator SHALL recognize bulleted lines that look like scenarios (e.g., lines beginning with WHEN/THEN/AND) and emit a targeted warning with a conversion example to `#### Scenario:`.
  a. Bulleted WHEN/THEN under a Requirement: WHEN bullets that start with WHEN/THEN/AND are found under a requirement without any `#### Scenario:` headers THEN emit warning: "Scenarios must use '#### Scenario:' headers", and show a conversion template: `#### Scenario: Short name / - WHEN ... / - THEN ... / - AND ...`
3. Normative keyword guidance SHALL not require English: The validation report SHALL include a warning for a non-empty requirement body without the literal English keywords `SHALL` or `MUST`. Normal validation SHALL remain valid when that warning is the only issue, while strict validation SHALL remain invalid because strict mode treats warnings as failures. A requirement with no body content before its scenarios SHALL remain an error.
  a. Non-English main spec: WHEN a main spec has a non-empty requirement body written without the English keywords `SHALL` or `MUST` THEN the validation report includes an RFC 2119 guidance warning AND normal validation succeeds
  b. Non-English change delta: WHEN an ADDED or MODIFIED requirement has a non-empty body written without the English keywords `SHALL` or `MUST` THEN the validation report includes an RFC 2119 guidance warning AND normal validation succeeds
  c. Strict validation preserves keyword enforcement: WHEN the same main spec or change is validated in strict mode THEN the warning causes validation to fail
  d. Requirement body is missing: WHEN a requirement has no body content before its scenarios THEN validation reports an error
4. All issues SHALL include file paths and structured locations: Error, warning, and info messages SHALL include:
  a. Source file path (`outline-spec/changes/{id}/proposal.md`, `.../specs/{cap}/spec.md`)
  b. Structured path (e.g., `deltas[0].requirements[0].scenarios`)
  c. Zod validation error: WHEN a schema validation fails THEN the message SHALL include `file`, `path`, and a remediation hint if applicable
5. Invalid results SHALL include a Next steps footer in human-readable output: The CLI SHALL append a Next steps footer when the item is invalid and not using `--json`, including:
  a. Summary line with counts
  b. Top-3 guidance bullets (contextual to the most frequent or blocking errors)
  c. A suggestion to re-run with `--json` and/or the debug command
  d. Change invalid summary: WHEN a change validation fails THEN print "Next steps" with 2-3 targeted bullets and suggest `outline-spec change show <id> --json --deltas-only`
6. Change validation SHALL report scenarios a MODIFIED block would drop: The `validate` command SHALL compare every `MODIFIED` requirement in a change against the main specs and report, as an error naming the delta file, each scenario the main spec still has that the `MODIFIED` block omits. A `MODIFIED` requirement replaces the whole requirement block, so archive refuses to apply one that drops a scenario; this is the same check, run without writing anything. The comparison SHALL match archive's operation order, comparing a `MODIFIED` that names the new header of a rename against the renamed requirement's scenarios. The check SHALL be silent when the main spec file or the requirement header is absent, because a `MODIFIED` written against a base that has not landed yet is a separate condition that archive gates. A main spec that exists but cannot be read SHALL be reported instead, since archive fails on it too. Validation run inside `outline-spec archive` SHALL NOT report these issues, because archive enforces the same check when it applies the deltas.
  a. MODIFIED omits an existing scenario: GIVEN the main spec's requirement has scenarios "A" and "B" WHEN a change MODIFIES that requirement with only scenario "A" and `outline-spec validate <change>` runs THEN report an error naming the delta file and scenario "B" AND exit with code 1
  b. MODIFIED names the new header of a rename: GIVEN the main spec has requirement "A" with scenarios "S1" and "S2" WHEN a change renames "A" to "B" and MODIFIES "B" with only scenario "S1" THEN report an error naming scenario "S2"
  c. MODIFIED header is not in the main spec: GIVEN a change MODIFIES a requirement header the main spec does not contain WHEN `outline-spec validate <change>` runs THEN do not report a dropped-scenario error for that requirement
7. Top-level validate command: The CLI SHALL provide a top-level `validate` command for validating changes and specs with flexible selection options.
  a. Interactive validation selection: WHEN executing `outline-spec validate` without arguments THEN prompt user to select what to validate (all, changes, specs, or specific item) AND perform validation based on selection AND display results with appropriate formatting
  b. Non-interactive environments do not prompt: GIVEN stdin is not a TTY or `--no-interactive` is provided or environment variable `OPEN_SPEC_INTERACTIVE=0` WHEN executing `outline-spec validate` without arguments THEN do not prompt interactively AND print a helpful hint listing available commands/flags and exit with code 1
  c. Direct item validation: WHEN executing `outline-spec validate <item-name>` THEN automatically detect if item is a change or spec AND validate the specified item AND display validation results
8. Bulk and filtered validation: The validate command SHALL support flags for bulk validation (--all) and filtered validation by type (--changes, --specs).
  a. Validate everything: WHEN executing `outline-spec validate --all` THEN validate all changes in outline-spec/changes/ (excluding archive) AND validate all specs in outline-spec/specs/ AND display a summary showing passed/failed items AND exit with code 1 if any validation fails
  b. Scope of bulk validation: WHEN validating with `--all` or `--changes` THEN include all change proposals under `outline-spec/changes/` AND exclude the `outline-spec/changes/archive/` directory WHEN validating with `--specs` THEN include all specs that have a `spec.md` under `outline-spec/specs/<capability-path>/spec.md`
  c. Validate all changes: WHEN executing `outline-spec validate --changes` THEN validate all changes in outline-spec/changes/ (excluding archive) AND display results for each change AND show summary statistics
  d. Validate all specs: WHEN executing `outline-spec validate --specs` THEN validate all specs in outline-spec/specs/ AND display results for each spec AND show summary statistics
9. Validation options and progress indication: The validate command SHALL support standard validation options (--strict, --json) and display progress during bulk operations.
  a. Strict validation: WHEN executing `outline-spec validate --all --strict` THEN apply strict validation to all items AND treat warnings as errors AND fail if any item has warnings or errors
  b. JSON output: WHEN executing `outline-spec validate --all --json` THEN output validation results as JSON AND include detailed issues for each item AND include summary statistics
  c. JSON output schema for bulk validation: WHEN executing `outline-spec validate --all --json` (or `--changes` / `--specs`) THEN output a JSON object with the following shape: `items`: Array of objects with fields `{ id: string, type: "change"|"spec", valid: boolean, issues: Issue[], durationMs: number }` `summary`: Object `{ totals: { items: number, passed: number, failed: number }, byType: { change?: { items: number, passed: number, failed: number }, spec?: { items: number, passed: number, failed: number } } }` `version`: String identifier for the schema (e.g., `"1.0"`) AND exit with code 1 if any `items[].valid === false` Where `Issue` follows the existing per-item validation report shape `{ level: "ERROR"|"WARNING"|"INFO", path: string, message: string }`.
  d. Show validation progress: WHEN validating multiple items (--all, --changes, or --specs) THEN show progress indicator or status updates AND indicate which item is currently being validated AND display running count of passed/failed items
  e. Concurrency limits for performance: WHEN validating multiple items THEN run validations with a bounded concurrency (e.g., 4–8 in parallel) AND ensure progress indicators remain responsive
10. Item type detection and ambiguity handling: The validate command SHALL handle ambiguous names and explicit type overrides to ensure clear, deterministic behavior.
  a. Direct item validation with automatic type detection: WHEN executing `outline-spec validate <item-name>` THEN if `<item-name>` uniquely matches a change or a spec, validate that item
  b. Ambiguity between change and spec names: GIVEN `<item-name>` exists both as a change and as a spec WHEN executing `outline-spec validate <item-name>` THEN print an ambiguity error explaining both matches AND suggest passing `--type change` or `--type spec`, or using `outline-spec change validate` / `outline-spec spec validate` AND exit with code 1 without performing validation
  c. Unknown item name: WHEN the `<item-name>` matches neither a change nor a spec THEN print a not-found error AND show nearest-match suggestions when available AND exit with code 1
  d. Explicit type override: WHEN executing `outline-spec validate --type change <item>` THEN treat `<item>` as a change ID and validate it (skipping auto-detection) WHEN executing `outline-spec validate --type spec <item>` THEN treat `<item>` as a spec ID and validate it (skipping auto-detection)
11. Interactivity controls: The CLI SHALL let users turn off interactive prompts.
  a. The CLI SHALL respect `--no-interactive` to disable prompts.
  b. The CLI SHALL respect `OPEN_SPEC_INTERACTIVE=0` to disable prompts globally.
  c. Interactive prompts SHALL only be shown when stdin is a TTY and interactivity is not disabled.
  d. Disabling prompts via flags or environment: WHEN `outline-spec validate` is executed with `--no-interactive` or with environment `OPEN_SPEC_INTERACTIVE=0` THEN the CLI SHALL not display interactive prompts AND SHALL print non-interactive hints or chosen outputs as appropriate
12. Parser SHALL handle cross-platform line endings: The markdown parser SHALL correctly identify sections regardless of line ending format (LF, CRLF, CR).
  a. Required sections parsed with CRLF line endings: GIVEN a change proposal markdown saved with CRLF line endings AND the document contains `## Why` and `## What Changes` WHEN running `outline-spec validate <change-id>` THEN validation SHALL recognize the sections and NOT raise parsing errors
13. Mermaid diagrams: Change validation SHALL report, as an error, each Mermaid code block in the change's Markdown files that Mermaid cannot parse, naming the file, the block's first line number, and Mermaid's parse message.
  a. Parsing uses the same Mermaid version the review page draws with, so a block that validates also draws.
  b. A change with no Mermaid blocks validates without loading Mermaid.
