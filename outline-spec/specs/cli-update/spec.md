# cli-update
As a developer using outline-spec, I want to update the outline-spec instructions in my project when new versions are released, so that I can benefit from improvements to AI agent instructions.

1. Update Behavior: The update command SHALL update outline-spec instruction files to the latest templates in a team-friendly manner.
  a. Running update command: WHEN a user runs `outline-spec update` THEN replace `outline-spec/AGENTS.md` with the latest template AND if a root-level stub (`AGENTS.md`/`CLAUDE.md`) exists, refresh it so it points to `@/outline-spec/AGENTS.md`
2. Prerequisites: The command SHALL require an existing outline-spec structure before allowing updates.
  a. Checking prerequisites: GIVEN the command requires an existing `outline-spec` directory (created by `outline-spec init`) WHEN the `outline-spec` directory does not exist THEN display error: "No outline-spec directory found. Run 'outline-spec init' first." AND exit with code 1
3. File Handling: The update command SHALL handle file updates in a predictable and safe manner.
  a. Updating files: WHEN updating files THEN completely replace `outline-spec/AGENTS.md` with the latest template AND if a root-level stub exists, update the managed block content so it keeps directing teammates to `@/outline-spec/AGENTS.md`
4. Tool-Agnostic Updates: The update command SHALL refresh outline-spec-managed files in a predictable manner while respecting each team's chosen tooling.
  a. Updating files: WHEN updating files THEN completely replace `outline-spec/AGENTS.md` with the latest template AND create or refresh the root-level `AGENTS.md` stub using the managed marker block, even if the file was previously absent AND update only the outline-spec-managed sections inside existing AI tool files, leaving user-authored content untouched AND avoid creating new native-tool configuration files (slash commands, CLAUDE.md, etc.) unless they already exist
5. Core Files Always Updated: The update command SHALL always update the core outline-spec files and display an ASCII-safe success message.
  a. Successful update: WHEN the update completes successfully THEN replace `outline-spec/AGENTS.md` with the latest template AND if a root-level stub exists, refresh it so it still directs contributors to `@/outline-spec/AGENTS.md`
6. Slash Command Updates: The update command SHALL refresh existing slash command files for configured tools without creating new ones, and ensure the OpenCode archive command accepts change ID arguments.
  a. Updating slash commands for Antigravity: WHEN `.agent/workflows/` contains `outline-spec-proposal.md`, `outline-spec-apply.md`, and `outline-spec-archive.md` THEN refresh the outline-spec-managed portion of each file so the workflow copy matches other tools while preserving the existing single-field `description` frontmatter AND skip creating any missing workflow files during update, mirroring the behavior for Windsurf and other IDEs
  b. Updating slash commands for Claude Code: WHEN `.claude/commands/outline-spec/` contains `proposal.md`, `apply.md`, and `archive.md` THEN refresh each file using shared templates AND ensure templates include instructions for the relevant workflow stage
  c. Updating slash commands for CodeBuddy Code: WHEN `.codebuddy/commands/outline-spec/` contains `proposal.md`, `apply.md`, and `archive.md` THEN refresh each file using the shared CodeBuddy templates that include YAML frontmatter for the `description` and `argument-hint` fields AND use square bracket format for `argument-hint` parameters (e.g., `[change-id]`) AND preserve any user customizations outside the outline-spec managed markers
  d. Updating slash commands for Cline: WHEN `.clinerules/workflows/` contains `outline-spec-proposal.md`, `outline-spec-apply.md`, and `outline-spec-archive.md` THEN refresh each file using shared templates AND include Cline-specific Markdown heading frontmatter AND ensure templates include instructions for the relevant workflow stage
  e. Updating slash commands for Continue: WHEN `.continue/prompts/` contains `outline-spec-proposal.prompt`, `outline-spec-apply.prompt`, and `outline-spec-archive.prompt` THEN refresh each file using shared templates AND ensure templates include instructions for the relevant workflow stage
  f. Updating slash commands for Crush: WHEN `.crush/commands/` contains `outline-spec/proposal.md`, `outline-spec/apply.md`, and `outline-spec/archive.md` THEN refresh each file using shared templates AND include Crush-specific frontmatter with outline-spec category and tags AND ensure templates include instructions for the relevant workflow stage
  g. Updating slash commands for Cursor: WHEN `.cursor/commands/` contains `outline-spec-proposal.md`, `outline-spec-apply.md`, and `outline-spec-archive.md` THEN refresh each file using shared templates AND ensure templates include instructions for the relevant workflow stage
  h. Updating slash commands for Factory Droid: WHEN `.factory/commands/` contains `outline-spec-proposal.md`, `outline-spec-apply.md`, and `outline-spec-archive.md` THEN refresh each file using the shared Factory templates that include YAML frontmatter for the `description` and `argument-hint` fields AND ensure the template body retains the `$ARGUMENTS` placeholder so user input keeps flowing into droid AND update only the content inside the outline-spec managed markers, leaving any unmanaged notes untouched AND skip creating missing files during update
  i. Updating slash commands for OpenCode: WHEN `.opencode/commands/` contains outline-spec-managed `outline-spec-*.md` command files for the configured profile (for example `outline-spec-propose.md`, `outline-spec-apply.md`, and `outline-spec-archive.md`) THEN refresh each file using shared templates AND transform command references to hyphen form (for example `/outline-spec-propose`), as for every tool whose command files are named `outline-spec-<id>` AND ensure templates include instructions for the relevant workflow stage AND ensure the archive command includes `$ARGUMENTS` placeholder in frontmatter for accepting change ID arguments
  j. Legacy OpenCode command path cleanup: WHEN a project still has command files under the legacy singular path `.opencode/command/` (for example `outline-spec-*.md` or `outline-spec-*.md`) THEN `outline-spec init` or legacy cleanup SHALL remove those files and generate replacements under `.opencode/commands/` AND `outline-spec update` SHALL NOT refresh files that remain only under `.opencode/command/`
  k. Updating slash commands for Windsurf: WHEN `.windsurf/workflows/` contains `outline-spec-proposal.md`, `outline-spec-apply.md`, and `outline-spec-archive.md` THEN refresh each file using shared templates wrapped in outline-spec markers AND ensure templates include instructions for the relevant workflow stage AND skip creating missing files (the update command only refreshes what already exists)
  l. Updating slash commands for Kilo Code: WHEN `.kilo/command/` contains outline-spec-managed `outline-spec-*.md` command files for the configured profile THEN refresh each file using shared templates wrapped in outline-spec markers AND ensure templates include instructions for the relevant workflow stage AND skip creating missing files (the update command only refreshes what already exists)
  m. Updating slash commands for Codex: GIVEN the global Codex prompt directory contains `outline-spec-proposal.md`, `outline-spec-apply.md`, and `outline-spec-archive.md` WHEN a user runs `outline-spec update` THEN refresh each file using the shared slash-command templates (including placeholder guidance) AND preserve any unmanaged content outside the outline-spec marker block AND skip creation when a Codex prompt file is missing
  n. Updating slash commands for GitHub Copilot: WHEN `.github/prompts/` contains `outline-spec-proposal.prompt.md`, `outline-spec-apply.prompt.md`, and `outline-spec-archive.prompt.md` THEN refresh each file using shared templates while preserving the YAML frontmatter AND update only the outline-spec-managed block between markers AND ensure templates include instructions for the relevant workflow stage
  o. Updating slash commands for Gemini CLI: WHEN `.gemini/commands/outline-spec/` contains `proposal.toml`, `apply.toml`, and `archive.toml` THEN refresh the body of each file using the shared proposal/apply/archive templates AND replace only the content between `<!-- OUTLINE_SPEC:START -->` and `<!-- OUTLINE_SPEC:END -->` markers inside the `prompt = """` block so the TOML framing (`description`, `prompt`) stays intact AND skip creating any missing `.toml` files during update; only pre-existing Gemini commands are refreshed
  p. Updating slash commands for iFlow CLI: WHEN `.iflow/commands/` contains `outline-spec-proposal.md`, `outline-spec-apply.md`, and `outline-spec-archive.md` THEN refresh each file using shared templates AND preserve the YAML frontmatter with `name`, `id`, `category`, and `description` fields AND update only the outline-spec-managed block between markers AND ensure templates include instructions for the relevant workflow stage
  q. Missing slash command file: WHEN a tool lacks a slash command file THEN do not create a new file during update
7. Archive Command Argument Support: The archive slash command template SHALL support optional change ID arguments for tools that support `$ARGUMENTS` placeholder.
  a. Archive command with change ID argument: WHEN a user invokes `/outline-spec:archive <change-id>` with a change ID THEN the template SHALL instruct the AI to validate the provided change ID against `outline-spec list` AND use the provided change ID for archiving if valid AND fail fast if the provided change ID doesn't match an archivable change
  b. Archive command without argument (backward compatibility): WHEN a user invokes `/outline-spec:archive` without providing a change ID THEN the template SHALL instruct the AI to identify the change ID from context or by running `outline-spec list` AND proceed with the existing behavior (maintaining backward compatibility)
  c. OpenCode archive template generation: WHEN generating the OpenCode archive slash command file THEN include the `$ARGUMENTS` placeholder in the frontmatter AND wrap it in a clear structure like `<ChangeId>\n $ARGUMENTS\n</ChangeId>` to indicate the expected argument AND include validation steps in the template body to check if the change ID is valid
